# Source discovery

Inventory only configured providers, containers, roots, and canonical references. Include the canonical profile explicitly even when outside those roots. An index or previous manifest is a discovery aid, not proof of coverage.

## Source eligibility and required references

Inventory answers which records could be found; it does not decide which records are eligible. A configured root is a search boundary, not an allow rule. Folder membership, extension, previous inclusion, filename proximity, or topical similarity alone never makes a candidate eligible. Check eligibility before invoking sensitive-record permission so an unrelated neighbor cannot become a grant request or a coverage failure.

Build the canonical seed set from the profile itself, verified identities in `source.canonical_records`, and the identities in fresh canonical authority or routing metadata owned by Remember Me or another identified record owner. Existing profiles without the new lists use those verified sources to resolve their canonical records. Do not infer canonical records from everything under a root or from an old manifest. If the required authority or identity cannot be resolved, ask only for that identity or authority; unattended runs retain a specific coverage gap.

Enumerate every configured candidate boundary independently, completing its pagination and retaining provider-scoped identity, aliases, and path mappings. Add the profile and verified canonical seeds to the candidate set even when they sit outside configured roots. A canonical record's direct, unambiguous file mention can identify a supporting record by its provider/container/resource identity; no special backup marker is needed. Resolve the mention using the provider's identity rules. A missing, ambiguous, inaccessible, excluded, or out-of-boundary required target is a coverage gap. Do not select the candidates until resolution has produced identity evidence.

Keep canonical routing separate from supporting-file mentions. Verified routing metadata can identify another canonical authority. A direct file mention in any canonical record can identify a supporting record. A supporting file's own links never qualify further targets, even when the parent was explicitly designated. A target still qualifies when it has its own canonical status, its own mention from a canonical record, or its own explicit user designation. `source.supporting_records` contains only such explicit designations; location and prior backup are not designation evidence.

Before the permission check, pass the run-local canonical identities, direct canonical mentions and their resolved target identities, explicit designations, excluded identities, and complete candidate identity set to `scripts/check_source_scope.py`. Keep the full inventory and its path mappings alongside the result for staging and the independent final-version check. The helper returns selected identities with inclusion provenance, out-of-scope candidates, and required-reference gaps. An ineligible candidate does not make eligible coverage incomplete. A gap in a required record does. The helper checks supplied declarations only; provider reads must establish fresh identity, authority, and resolution evidence.

The input is disposable JSON with `schema_version: 1`, `profile`, `canonical_records`, `canonical_mentions`, `user_designations`, `excluded`, and `candidates`. Identity objects use `source_provider`, `source_container`, and `source_id`, where `source_id` follows the existing immutable-ID or documented fallback rules. Each canonical record includes its `owner` and bounded `evidence_reference`. Each canonical mention has `from`, `reference`, `state`, and `targets`; `state` is `resolved`, `ambiguous`, `inaccessible`, `not-found`, or `out-of-scope`. A resolved mention has exactly one target. Each explicit designation includes a bounded `designation_reference`. The helper does not read YAML, search providers, authenticate supplied evidence, inspect content, or grant permission.

```text
python scripts/check_source_scope.py RUN_INPUT/source-scope.json
```

Exit 0 means the supplied required identities resolved; exit 1 means the valid packet contains coverage gaps; invalid input exits 2. Read its JSON result in every case. Only selected identities proceed to permission checks. Apply class, credential, destination, and other exclusions under their existing owners as well; this helper does not replace those checks.

`destination.exclusions` applies only to extra-file checks and preservation in the GitHub destination. It does not remove any configured source root, authorize skipping source reads, or turn a source retrieval miss into a deletion.

- Maintain one run-local inventory keyed by `(provider, container, immutable ID)`, with the strongest documented fallback when IDs are unavailable. Track root/page cursors and visited pointer identities separately. Deduplicate overlapping roots and aliases before fetching content; preserve all relevant path mappings and report conflicting identities.
- Complete each listing's pagination once during the initial pass. Resolve canonical routing pointers and direct mentions from canonical records; do not recursively follow links from supporting files. Record out-of-scope targets without expanding scope. Deduplicate aliases and cycles in canonical routing without suppressing required final checks; a repeated alias or a fully traversed cycle alone is not a coverage gap. Repeated pagination cursors, inaccessible pages, or truncated results may prevent complete enumeration: resolve them or mark the run incomplete, never infer deletion.
- Batch metadata and content reads when the provider supports it. Fetch each included identity once per capture phase, reusing the resulting bytes and hashes within that phase. Daily runs may reuse verified bytes when trustworthy versions match; otherwise read and hash. Weekly runs start with a fresh inventory and read all included bytes independently of the daily cache.
- Preserve original bytes and extensions for YAML, JSON, Markdown, binary, and extensionless files. Never convert text, normalize line endings, or regenerate YAML during capture. For provider-native exports record the chosen representation and source version in the manifest and explain fidelity/history limits in the receipt.
- Classify known sensitive records from the authorized source metadata and user instructions; apply [sensitive-record permission](configuration-and-schema.md#sensitive-record-permission). Do not infer a grant from durable designation or a previous successful backup. Keep denied candidates distinct from confirmed deletions. Remote binary read limits follow [remote byte retrieval](weekly-reconciliation.md#remote-byte-retrieval); source bytes are never a substitute for remote recovery evidence.
- When complete listing is unavailable, use bounded searches scoped to the configured roots and record query coverage. Search results alone do not prove completeness. Report inaccessible or ambiguous candidates and retain their last verified copies.
- Perform the required final inventory/version check separately; deduplication must not suppress this check or the independent remote verification. Retry moving records a bounded number of times, then fail complete publication if coherent capture cannot be established.

Record listing/page calls, content reads, duplicate identities, pointer cycles, retries, and access limits in the receipt. Compare an overlapping-root, paginated fixture before and after changes: inventory identities and hashes must match while redundant initial-phase reads decrease. The issue's named conversations are reported context unless actually available; do not invent observations from them.
