# Weekly reconciliation

Reconciliation is an independent coverage and recovery audit, not a slower daily sync. It must rediscover the complete configured scope without trusting the daily cache or prior manifest.

1. Load the current canonical profile and apply [sensitive-record permission](configuration-and-schema.md#sensitive-record-permission). Enumerate every configured source root, page, and authoritative pointer using [source discovery](source-discovery.md). Include the profile YAML and all authorized canonical file formats. Record inaccessible, ambiguous, duplicate, and out-of-scope candidates separately; deduplicate within this fresh run without trusting the daily cache. When destination exclusions exist, pin the current branch commit and complete protected-tree inventory before reconciliation, following [destination preservation evidence](destination-preservation.md). Missing or revoked permission preserves the affected prior copy and leaves the complete audit incomplete.
2. Read every included current, supporting, and history record and calculate the exact stored-byte hash. Compare provider/container identity, immutable ID, path, role, source version, size, and hash with the latest reachable Git snapshot.
3. Check missing and extra records, confirmed deletions versus retrieval misses, renames, duplicate mappings, case collisions, index pointers, exclusions, branch ancestry, manifest consistency, and repository structural integrity. Run the offline snapshot validator on a fresh download.
4. Repair recoverable current-state omissions through the same staged, atomic, remotely verified publication path. Preserve excluded directories from the pinned destination base; do not reconstruct them from source discovery or copy them from a stale manifest. Require `staged_preserved` before publication and `content_preserved` after independent content readback. Do not manufacture unseen intermediate versions. If source revisions expose continuity, record recoverable gaps; otherwise report historical coverage as unknown.
5. Reconstruct the complete latest snapshot from GitHub into isolated scratch storage and verify all hashes and mappings, subject to an explicitly authorized unchanged-file verification reuse below. Periodically reconstruct an older commit as a recovery drill. Test provider restoration only in an isolated destination when supported; it may require new source IDs and pointer remapping.
6. Follow [receipts and reporting](receipts-and-reporting.md); the receipt separates `current_state_complete`, `history_coverage`, `repaired_items`, `unrecoverable_gaps`, `source_access_limits`, and `restore_test`. Include discovery counters and update the README's latest weekly result even when incomplete or failed. After independent operational readback, require full `preserved` status for excluded directories. Alert when the audit is incomplete or the last verified daily-equivalent run exceeds the configured threshold, when configured.

Never treat a successful Git API response as reconciliation proof. The audit succeeds only after fresh remote reads and reconstruction checks pass, or all affected files meet the explicit reuse policy below. A retrieval miss never authorizes removing a current mirror entry.

## Remote byte retrieval

Source SHA-256, Git blob identity, remote commit reachability, independently retrieved byte SHA-256, and complete reconstruction prove different facts. A matching remote blob ID alone does not complete the recovery drill. A user assertion also cannot replace missing remote bytes.

1. Pin the intended reachable commit, tree path, blob identity and expected size/SHA-256 from the checked snapshot. Inspect the current tool capabilities and observed errors. Do not retry a text-only route that rejects binary data merely because the filename has changed.
2. Use a supported binary route when available: a content/blob API that actually returns base64 bytes, an authenticated raw/blob download, or an authorized Git checkout/archive into isolated scratch storage. These are conditional alternatives, not promised capabilities. Keep authentication in its credential facility; do not copy signed download URLs or tokens into logs. Bound attempts to the available distinct routes and the existing retry policy; stop when no supported route remains. Do not execute downloaded files.
3. Save the actual remote payload in scratch. For base64 JSON responses, extract only the declared base64 content, not a display string or metadata placeholder. Run `scripts/verify_download.py PAYLOAD --encoding raw|base64 --byte-size N --sha256 HASH`, optionally with `--output NEW_SCRATCH_FILE` to materialize verified decoded bytes without overwriting an existing file. Reject empty nonempty-file payloads, truncation, invalid encoding, and size/hash mismatch. Do not substitute the source or daily cache for an independent remote download.
4. Retain route, executed retrieval outcome, pinned commit/blob identity, expected/observed size/hash and limitations in bounded receipt metadata; never retain record contents or credentials. The helper proves only supplied bytes match expectations; the run must establish their independent remote origin, branch reachability and source mapping.
5. Reconstruct the full latest snapshot, and the selected older snapshot when performing that drill, before setting their fresh full recovery checks true. If either attempted drill is incomplete and the missing bytes do not qualify for the explicit unchanged-file reuse policy below, finalize this weekly run as `incomplete` or `failed`, with `current_state_complete: false` and explicit affected-record limitations. Distinguish any independently verified changed-file publication from full recovery. Use null `snapshot_commit` when the claimed snapshot has passed neither independent verification nor the explicit reuse policy; an optional `published_content_commit` records publication without granting verification credit. Preserve prior verified content and historical receipt claims unchanged.

An optional user match attestation remains task evidence unless the user explicitly authorizes durable unchanged-file reuse as below. An unscoped assertion, stale attestation, matching Git SHA-1 alone, or successful API response cannot turn a failed recovery check into `verified`. Describe a transport problem as fixed only after actual independent retrieval and size/SHA-256 verification through the intended route.

## User-authorized unchanged-file reuse

When the user explicitly requests it, retain metadata for a user-reported GitHub raw download and matching size/SHA-256 in the destination index's `manual_remote_verifications` array. This is a scoped user-owned exception to repeated remote-byte verification, not a blanket waiver or a source-record change. Follow the schema in [configuration and snapshot schema](configuration-and-schema.md#manual-remote-verification-reuse). Preserve the entries when rebuilding the index; do not revive revoked entries or update their evidence automatically.

Each weekly run must freshly capture and hash the source, match its complete scoped identity and exposed version, verify destination branch reachability and read the selected commit's tree/blob metadata independently. Match the manifest to that fresh source capture. Serialize one entry, that freshly checked record, destination, freshly observed `remote_blob_id`, and current ISO date `at` to run-local JSON. `scripts/check_manual_verification.py INPUT.json` exits 0 only for exact eligible reuse; it does not establish freshness or provenance of supplied inputs. Multiple matching entries are ambiguous and must not be reused.

If eligible, do not let inability to download that unchanged blob alone make the run incomplete. Materialize the freshly captured exact bytes for local snapshot validation and report their source provenance; distinguish them from this run's remote downloads. For an older drill, independently establish that the older manifest maps the same scoped file and bytes and its tree contains the exact approved blob; otherwise the exception does not apply. Any changed identity, exposed version, path, size, SHA-256, destination or blob, revoked permission, missing evidence, or failed remote metadata check requires fresh verification and remains a blocker when unavailable. Continue all other discovery, permissions and recovery checks.

A run can report `verified` or `verified-no-change` when every required check passes under this explicit policy. Set `checks.manual_verification_reuse` and `checks.recovery_policy_satisfied` true, and include `reused_manual_verifications` with IDs, affected snapshot commits and evidence dates. Explain the reused checks in `coverage_limits` and `restore_test`. Omit `full_latest_restore`/`full_older_restore` for any drill performed under this policy: those flags mean a fresh full remote reconstruction. Do not set them true for reused evidence or override a finalized false check. Preserve old receipts; the October 11 incomplete run stays incomplete. Reuse does not establish that the automated binary transport was repaired.
