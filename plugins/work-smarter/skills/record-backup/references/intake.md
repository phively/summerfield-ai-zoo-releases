# Backup intake

Use for requested setup, missing or incomplete configuration, conflicting profile identities, or material changes to scope, destination, formats, or reporting. A valid existing profile goes directly to the requested run. In unattended mode, report the exact missing fields and stop the affected operation.

1. Locate the user-designated canonical profile by its stable identity or known path. Do not conduct an unrestricted Library search to guess which of several profiles is authoritative. Resolve ambiguity with the user. Reuse established values and ask only for missing decisions in small, related groups.
2. Establish source providers, container IDs, authorized roots/pointers, owners/roles, and exclusions. Scope is based on authority and inclusion rules, not a Markdown suffix. Include the canonical backup YAML itself; confirm inclusion of other canonical formats, including binary and extensionless files. Provider-native exports require an explicit representation choice and coverage limits. For sensitive non-credential records, apply [sensitive-record permission](configuration-and-schema.md#sensitive-record-permission): ask only for missing identity, destination, class, duration, exact-hash versus future-version scope, and task-only versus persistent permission. General first-publication approval alone is not a sensitive-file grant.
3. Establish the exact GitHub repository and branch. Read repository identity, privacy, branch state, and transport capability without publishing. Check credential availability without requesting or copying secret values into the profile.
4. Establish the canonical profile location, a durable receipt fallback outside disposable scratch storage, timezone, optional daily/weekly schedules, notification destination or disabled state, deletion/history policy, and any freshness threshold. Manual-only setup needs no scheduler expressions. Receipt history is retained; the README displays the latest weekly result and seven daily results.
5. Present the concrete included/excluded scope, profile location, owner and permitted maintainer, destination, and remaining access limits. Obtain authorization for missing material choices and profile creation/changes, using authorization already supplied in the conversation. Save one credential-free profile outside the installed skill, reread it, and check it against the schema. Preserve unrelated fields; report unavailable or partial writes without claiming persistence or creating another authority. If an existing profile contains secrets, require their removal to a credential facility before backing it up; do not publish a silently redacted substitute as an exact copy.
6. State what is ready and what remains unavailable. Creating configuration, creating scheduler jobs, and first publication are separate actions; perform only those requested. Do not imply a scheduled job exists from YAML alone. Before first publication use the profile's exact destination and the applicable authorization.

For existing schema-version-1 profiles, preserve source identities and paths. Add missing profile identity/reporting fields with the user's authorized choices; do not change scope or invent a fallback location. Existing historical snapshots remain readable without migrating them.
