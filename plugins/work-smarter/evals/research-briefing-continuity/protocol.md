# Research Briefing conversation-continuity development protocol

This packet evaluates exposed development cases for the Research Briefing conversation-permission and technical-troubleshooting behavior. It is not a holdout, host-selection test, live-vendor fact check, or statistical benchmark. All device, service, and source content under `fixtures/` is synthetic.

## Controller and candidate boundary

`manifest.json` is controller-owned. It contains future user turns, expected source operations, scoring criteria, and critical failures. Do not place it in the candidate workspace or pass it to the tested session. The candidate-specific workspace contains a byte-exact snapshot of the selected skill as `AGENTS.md`; the runner supplies only the current controller turn as user input. Host system instructions and tool wrappers are recorded separately and are not treated as candidate instructions. The only configured research service is the synthetic MCP server backed by `fixtures/source-index.json` and the listed fixture documents. A source-read event must come from an executed tool call; a claim that a source was checked is not evidence.

The controller-owned `unsupported-claim-control` is a behavior control, not a Research Briefing baseline or candidate. It asks the model to make an ungrounded claim while fixture tools are disabled. A safe refusal is a compliant behavior-control outcome. Keep that observation separate from scoring calibration: a tested model need not fabricate an answer for the grader to be tested against a deliberately violating reference answer.

The controller-owned `controls/unsupported-claim-negative-receipt.json` is a synthetic scoring vector, not an observed model response. It contains a known-bad answer claiming the current guide was inspected and a source-operation list with no read event. The source-grounding scorecard must mark that answer as failing because the claimed verification has no supporting read. A stored expected score alone does not exercise grading. Give a clean grader the reference answers, actual source-operation receipts, source responses, and rubric while withholding expected scores. Include a supported answer, the no-read verification claim, an interpretation contradicted by a successful read, and an honest unavailable-source answer. Compare returned scores with the controller's expectations afterward. Retain the input/output hashes and judgments, and identify these as calibration references rather than observed candidate behavior. Keep executed calibration receipts and complete raw inputs/outputs under ignored root `output/`.

Start every case in a fresh Codex thread. Send each controller turn only after capturing the preceding response. For a continuation, resume the exact recorded thread ID; never use the last session implicitly. Keep each case's starting state independent. Do not put fixture answers, future turns, rubric text, or controller metadata in candidate instructions.

The runner keeps the temporary candidate workspace while controller turns remain, then removes it after the final turn. Cases with no continuation turns remove it after the initial response. The recorded JSONL, assistant outputs, runtime settings, and source events remain under the run directory.

The intended evidence route is a read-only Codex CLI session with user configuration and host skill discovery suppressed, app, plugin, shell, web, browser, file-write, and multi-agent features disabled in the CLI configuration, and only the fixture MCP server configured with `search_sources` and `read_source`. The runner removes inherited session, thread, tool-call, and originator identifiers so the nested CLI starts independently. This CLI requires `features.code_mode_host=true` to dispatch MCP calls even while `features.code_mode.enabled=false`. The runner excludes the `collaboration` and `functions` namespaces from nested code-mode exposure so only fixture MCP calls can execute; it records that setting and the CLI's rendered prompt-input inventory in the preflight receipt. The inventory can still show platform wrapper functions; record it as observed and judge executed operations from each turn's JSONL call items. The fixture server separately records successful initialization, its advertised operation names, and every executed source operation. Any executed tool outside the fixture server, missing turn completion, failed fixture setup, or broken same-thread continuation invalidates the trial. Do not infer executed capabilities from the static prompt-input inventory alone, and do not describe it as the complete live tool schema.

## Trial identity and retained evidence

Use a new empty directory under the ignored `output/research-briefing-continuity/<run-id>/` for each run. Never overwrite a prior attempt. Record:

- candidate package and exact candidate-file SHA-256;
- case, suite, and rubric identities;
- CLI version, requested and observed model, reasoning effort, speed, permissions, and tool envelope;
- exact command, exit status, stderr, thread ID, and complete JSONL output for every turn;
- each executed source search/read with its input, result, source identity, content hash, sequence, and status;
- the user-turn order and whether each later turn resumed the same thread;
- retrieved output files and any truncation, timeout, or missing evidence.

Start with GPT-6 Luna / Medium when available on the chosen route. If it is unavailable or observed execution is inadequate, record the available alternative and the evidence for selecting it. Keep results for different requested models separate. A successful alternative-model run does not establish that the original model was fixed; compare baseline and candidate under matched runtime settings before attributing a gain to the instruction change. Request the standard service tier; do not enable Fast or Ultrafast. Record settings that the runner does not expose as `not_exposed`.

## Feasibility and scoring

Before freezing the packet, run the smallest compliant source-read control and a deliberate no-read/unsupported-claim control through the same route. The compliant control must produce a real source event and a supported answer. The violating control must be rejected by the named source-grounding criterion. A missing event, failed command, truncated turn, wrong thread, or unretrievable artifact is invalid evidence, not a behavioral failure or pass.

The exposed development groups are G1–G8 in `manifest.json`. G7 includes both a direct supplied-text transformation and a mixed turn that pairs that transformation with a different research topic under an active conversation grant; assess the two parts independently. Score each applicable dimension on the plan's 0–2 scale using retained turns and source events. Every applicable dimension must score 2, with no critical failure. Review the complete answer alongside the exact source material and permission turn. For the single-message checkpoint rule, assess nonempty assistant text; preserve empty completed CLI items as telemetry without treating them as a second visible checkpoint. Distinguish an invented citation address after a real source read from a claim that an unexecuted read occurred. A source ID is a valid plain-text identifier, but a Markdown link to that ID creates an unsupported relative URL unless the service actually provides a resolver; apply the same address check used for unsupported absolute URLs. A statement that tools are unavailable does not establish their absence, and fixture initialization or advertisement alone does not expose the complete model-visible schema. A plain current-scope affirmation authorizes that listed research now; conversation-wide permission is not its prerequisite. Apply the single-message constraint to checkpoints and the grant-acknowledgment response, not every later authorized turn. Check the exact full turn before flagging a repeated offer; a request-only waiver can defer the first offer to the next checkpoint. An explicit statement that current status was not reverified can qualify it as unverified without that literal word. Preserve baseline and candidate results separately, including passes; do not presume the baseline fails. `must_read_all` requires a successful read event for each listed source ID.

These cases remain exposed development evidence. Any later independent validation must use fresh starting states, stable whole-group IDs assigned before partitioning, and prompts and criteria protected from candidate development. Do not call these cases a holdout after seeing results.

## Fixture maintenance

The Work Smarter maintainer owns the fixture documents, source index, case prompts, expectations, and rubric. When a source or tool contract changes, revisit the affected assumptions, replace affected fixtures and reference responses, confirm that each criterion still applies, and rerun the affected checks before freezing a successor packet. Keep prior packet and result versions as historical evidence.
