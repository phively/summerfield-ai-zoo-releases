## Scope and authority

This review covers R5-R12, AE4-AE9, and KTD12 in the Remember Me benchmarks and backup exclusions plan (private planning record). The approved Product Contract decision **Descriptive evidence with current policy retained** narrows R12 to existing deterministic controls, instruction review, and disclosure of unrun activated behavior. KTD12 credits the user's prior provider publication and restore/recovery exercise for unchanged mechanics. Neither decision turns that attestation into independently verified evidence or turns an unrun exclusion-aware operation into a pass.

The Record Backup workflow is instruction-driven. The repository has offline policy, snapshot, preservation, and reporting helpers, but no central provider enumerator, publisher, or YAML profile parser. The [mode fixture protocol](record-backup-destination-exclusions/protocol.md) describes the synthetic tests and their limits.

## Acceptance example coverage

- **AE4:** The synthetic modes and policy fixtures show an arbitrary user-selected root can be exempted while its contents remain outside the managed record manifest. The plan's `canonical/career-opportunities/` is an example; no directory name is hard-coded and the fixture does not inspect that real directory.
- **AE5:** Exact component matching leaves prefix neighbors outside the rule. Tests also retain missing/hash-mismatched managed-record failures and unexpected-file failures elsewhere.
- **AE6:** Policy tests reject roots overlapping records, receipts, README, the profile, and the manifest; destination roots also reject `.git`. They test synthetic inputs, not profile editing.
- **AE7:** Synthetic preservation inventories fail on protected-tree changes and stale/concurrent bases. A helper result only has preservation meaning when the workflow independently establishes the declared baseline and publication reads.
- **AE8:** Receipt checks keep incomplete/failed outcomes distinct, require the evidence fields for verified outcomes, and retain older receipt history. They do not execute a later reconciliation or prove that it actually repaired and verified a snapshot.
- **AE9:** Historical/current packet binding is covered by the synthetic mode regression. Restore instructions use a packet derived from a pinned historical snapshot for validation only, keep it separate from current write authority, and require a profile diff and explicit confirmation before any profile restore.

## Limitation and defect review

Static inspection found no demonstrated R6-R11 implementation defect to report. It did confirm a correctness-critical R5 evidence boundary: `destination_policy.validate_policy` explicitly cannot prove freshness, faithful YAML extraction, user consent, or publication authority. It accepts independent expectations supplied by its caller and checks that the packet, expectations, and staged profile bytes agree. A fabricated but internally consistent packet could therefore pass if a caller failed to retain the required independent canonical-profile and destination reads. The instruction contract requires those reads and applicable authorization, but these offline tests do not verify that runtime behavior. Treat this as an unverified workflow property, not as proof that canonical authority was checked; if an actual caller cannot provide that evidence, it is an actionable R5 correctness gap.

The preservation and reporting helpers have the same evidence boundary for provider facts: hashes, tree reconstruction, and receipt consistency prove the supplied inputs agree, not that a provider supplied them or that a publication occurred. Do not upgrade these helper checks to live publication, restore, or user-consent evidence.

This documentation-only review does not rerun tests. The shared U7/U3 implementation wave was active, and U6 requires no new test cases or model trials. The previously recorded suite results remain historical evidence; they are not reported here as fresh execution.
